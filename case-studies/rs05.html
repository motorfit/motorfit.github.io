RS05 study#

MotorFit uses this study as a worked example of acquisition, identification, freezing and validation. The reusable workflow is described in the workflow guide; this page records the measured instance.

Experiment#

Item

Recorded study

Motor

RobStride RS05, UID 542b38001c443916

Fixture

Measured pendulum with 100/200/500 g weights and load-specific fasteners

Formal recordings

37 per load; 111 total, 227,511 original samples

Split

32 training / 16 gain validation / 24 load validation / 36 final test / 3 long test

Acquisition

Vendor RS05 C++ library through the SocketCAN adapter; independent wire capture

Identification

BAM M1–M6 comparison; frozen M1 selected under the recorded protocol

The example includes the frozen M1 snapshot; new fits must write elsewhere. The local archive stores the full model collection in data/rs05/models/, including comparison/ for the other five selected BAM families and provenance/ for the fitting protocol and selection freeze. Its data/rs05/formal-v3/manifest.json preserves the original record IDs, splits and hashes. See fixture properties for measured masses and the distinction between the identification fixture and finite-body CAD replay.

Each load used Kp 10/20/30, with Kd values respectively:

Weight

Kd at Kp=10 / 20 / 30

100 g

0.5 / 0.6 / 0.8

200 g

0.6 / 0.8 / 1.0

500 g

0.9 / 1.2 / 1.5

These settings describe this fixture. Earlier 200 g Kp=30/Kd=0.5 trials showed persistent oscillation and are outside the formal dataset. The completed 100 g run 15 has a documented wrapper-finalization interruption; its recording and verification evidence remain included.

Original acquisition format#

The recordings used the vendor RS05 C++ source with an RS05-specific SocketCAN caller. New acquisition uses motorfit record; the recorded reference schedules describe the original experiment.

To reconstruct a BAM export from an original CSV/wire capture:

uv run motorfit export-formal --record <original-record-directory> \
  --metadata <that-records-raw.json> --output <new-raw.json>

Use metadata from that same recording: motor identity, coordinate, fixture and split must match its capture. This is an offline data converter and requires no vendor library.

RS05 reference acquisition#

The supplied RS05 dataset was recorded with a C++ collector using the following timing:

Trajectory

Schedule

Nominal total

sin_time_square, sin_sin, up_and_down

2 s initial hold + 12 s excitation + 4 s return + 2 s final hold

20 s

lift_and_drop

2 s initial hold + 4 s lift + 14 s torque-disabled observation

20 s

long_sweep

2 s initial hold + 30 s excitation + 4 s return + 2 s final hold

38 s

The schedule contains 2,001 or 3,801 timestamps at 100 Hz, including the final nominal endpoint. These are properties of the recorded experiment. The current Python recorder uses the configurable duration described above; choosing 20 seconds does not reproduce these staged schedules.

The initial/final holds provide observation windows around motion. The lift/drop protocol keeps collecting feedback while the actuator is disabled. The long sweep supplies an additional extended test. These choices describe the recorded experiment; a new actuator study should select and document its own windows.

Results and limits#

For the MuJoCo 3.17 full-option baseline, final-test position MAE is about 2.220 mrad. The representative 200 g release still has a stop bias of roughly 7 mrad and small measured retreat that frozen M1 does not reproduce. Aligning the disable event to STOP send improves early timing but does not explain that residual. See measured limitations.

The recording, firmware, controller, fixture and validation versions define the scope of these results. Other units, controller families and robot contact tasks need their own identification and evaluation evidence. Use bring your own motor to adapt the workflow.

What to reproduce#

Git includes the self-contained three-record example, its frozen M1 model and saved predictions. The complete study belongs to the local archive under data/rs05/, which is ignored as a whole, including manifests and summaries:

data/rs05/
  formal-v3/     # 111 recordings, processed data, captures and manifest
  models/        # fitted models and selection provenance
  results/       # predictions, comparisons, diagnostics and videos
  assets/bench/  # source CAD, meshes and mass-property manifest
  scenes/release/
  environments/ # recorded runtime versions
  artwork/       # reference renders and figure-production materials

If a supplied archive includes an adjacent SHA256SUMS, check it with sha256sum -c SHA256SUMS before extraction. Full-study commands then verify the model and all indexed inputs:

uv run motorfit verify --dataset data/rs05/formal-v3/manifest.json
uv run motorfit audit-feedback \
  --dataset data/rs05/formal-v3/manifest.json --output outputs/rs05-audit

Use the validation guide for CAD replay, solver options and release timing comparisons. The archive’s data/rs05/results/README.md indexes model-selection evidence, frozen BAM predictions, three-backend comparisons, feedback audits and residual studies. See the repository policy for tracking rules.

CAD and solver options#

The included physics adapters implement frozen M1 with the recorded MIT-style controller and pendulum dynamics. BAM fitting supports M1–M6; replaying another family or rig requires the corresponding physics integration. A new manifest alone does not supply that integration.

uv sync --frozen --extra simulation
uv run --frozen --extra simulation motorfit replay \
  --dataset data/rs05/formal-v3/manifest.json --engine mujoco --dt 0.002 \
  --scene-assets data/rs05/assets/bench --output outputs/cad-replay

Without --scene-assets, replay uses the equivalent point-load fixture used for fitting. --fixture-model identified_point gives the CAD appearance with identification-equivalent inertia. --ablations evaluates delay/friction/armature removal on the training split.

uv run --frozen --extra simulation motorfit replay \
  --dataset data/rs05/formal-v3/manifest.json --engine mujoco --dt 0.002 \
  --scene-assets data/rs05/assets/bench --options configs/simulation/asroballet-option.xml \
  --friction default --output outputs/solver-default

The option fragment is a standalone benchmark configuration; no robot XML is edited. --friction original retains the benchmark friction constraint. The common replay entry supports --engine newton and --engine mjlab when the matching optional environment is provided. It checks requested options instead of quietly disabling unsupported features. Optional runtime versions and limitations are documented in the environment guide.

Release timing#

uv run --frozen --extra simulation motorfit release-replay \
  --dataset data/rs05/formal-v3/manifest.json --scenes data/rs05/scenes/release \
  --output outputs/release-alignment

This builds a small C++ helper with the installed MuJoCo library and runs the 27 release records at 62.5 microseconds for the processed enable flag, STOP send and two acknowledgments. Use --record <id> for a single record; --dt 0.000125 or 0.00025 for timestep comparisons. Bus-clock variants are available through --cases stop_tx_bus stop_ack1_bus stop_ack2_bus. The helper splits an integration step at the event without an extra command-delay shift. The model and measured trajectories stay fixed. These times are sensitivity assumptions, not measurements of the power stage’s actual current decay.

Render saved trajectories#

MUJOCO_GL=egl uv run --extra simulation python scripts/render_replay.py \
  --dataset data/rs05/formal-v3/manifest.json --source data/rs05/results/replay/cad-baseline \
  --assets data/rs05/assets/bench --output outputs/video --grams 200 \
  --trajectory lift_and_drop --preview 8

The renderer uses saved states from all three backends and a common camera. Omitting --preview writes a full video; ffmpeg is required. With all loads/trajectories selected, --concat also builds three full-length compilations. The renderer has a portable bundled Matplotlib font fallback; --font accepts a preferred font file. The provided Chinese videos remain the original validated outputs and are not relabelled as timing-corrected runs.

Complete replay videos#

The separate archive contains these files under data/rs05/results/media/:

  • rs05_200g_all_profiles_complete.mp4 — 118.033 s

  • rs05_500g_all_profiles_complete.mp4 — 118.000 s

Each compilation contains four 20-second clips and a roughly 38-second long sweep, in full at original speed. Timing details explain the experiment windows and frame rounding. Videos are available in the separate full data archive.

The three panels render saved MuJoCo, Newton and mjlab states with a shared camera, time axis and measured position reference. They show the CAD baseline study, rather than the later release-timing sensitivity runs. They are rendered comparisons, not three native simulator UI captures.

How replay duration is calculated#

The renderer uses the saved processed samples at their recorded dt, at 1× speed:

source duration = number of processed samples × dt
video frames    = ceil(source duration × 30 fps)
video duration  = video frames / 30 fps

The last sample is held through its final display interval. Video duration is rounded up to a whole frame. Videos cover the complete processed record; no fixed 20-second crop is applied. Position interpolation is for display only and does not rerun the simulator.
